## 三、入库字段与实测状态

三套集合都只有两个显式字段，其余走动态字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `chunk_id` | VARCHAR(256)，主键 | `chk_` + SHA256，非自增 |
| `vector` | FLOAT_VECTOR(1024) | 索引 FLAT，度量 COSINE |

可查到的动态字段：`content_sha256`、`start_line`、`end_line`、`entity_type`、`symbol_id`、`repository_id`、`snapshot_id`、`commit_sha`、`file_path`、`canonical_name`、`name`、`chunk_index`、`embedding_model`、`embedding_digest`；段落与字符段另有 `symbol_ids`（多值）、`source_start_char` / `source_end_char`、`character_count`、`paragraph_index`。

正文 `code` 不写进 Milvus，存在 `reports/platform/index*.json` 里，检索命中后按 `chunk_id` 回本地索引取原文。这是团队的做法，好处是向量库只存检索必需字段，正文改动不影响向量记录结构。

两处口径与规范文字不同，以实现为准并留档：

1. `chunk_id` 规范写 `[snapshot_id, symbol_id, chunk_index, chunk_content_sha256]`，实现是 `chk_` + SHA256(`[snapshot_id, symbol_id, profile_id, index, content_hash]`)。多了 `profile_id` 与 `chk_` 前缀。好处是同一段源码在三种切法下 chunk_id 天然不撞键。
2. 向量化输入是 `canonical_name + "\n" + code`，不是纯正文；检索时 query 前加固定指令前缀 `Instruct: Retrieve Java source code that answers the business logic question.\nQuery: `。两处前缀必须成对使用，只加一头会让分数整体掉下来。

## 四、三套检索评测

工作台（`workbench/serve.py`，端口 8777）已切到上述三套集合，检索带 `repository_id` + `snapshot_id` 双过滤；方法模式下再追 `entity_type == "Method"`，只召回方法，字段段不参与排序。

判定口径：首位片段的行区间盖住期望方法 ≥ 50% 才算命中。字符窗口会跨方法，擦边不算，免得把"顺手扫到两行"记成命中。另记 Top-5 里有没有片段达标。

| 切法 | 首位命中 | Top-5 召回 | 检索耗时 |
| --- | --- | --- | --- |
| method | 5/8 | **8/8** | 740ms |
| paragraph | 5/8 | **8/8** | 279ms |
| character 400/80 | 1/8 | 1/8 | 264ms |

逐题覆盖率（数值＝首位片段盖住期望方法的比例）：

| # | 问题 | 期望 | 方法 | 段落 | 定长 |
| --- | --- | --- | --- | --- | --- |
| 1 | 借书前需要检查哪些条件？ | borrowBook | 0 | 0 | 0.304 |
| 2 | 有未还图书时还能再借吗？ | borrowBook | 0 | 0 | 0.304 |
| 3 | 图书排行榜按什么排序？ | borrowRank | 0.969 | 0.969 | 0.219 |
| 4 | 删除已借出的书会怎样？ | deleteBook | 0.969 | 0.969 | 0.344 |
| 5 | 归还图书的流程？ | returnBook | 0.979 | 0.979 | 0.146 |
| 6 | 新增图书要录入哪些信息？ | addBook | 0.969 | 0.969 | 0.125 |
| 7 | 怎么查看所有读者的借阅情况？ | showReader | 0.938 | 0.938 | 0.5 |
| 8 | 系统启动后先做了什么？ | startSystem | 0 | 0 | 0 |

三个结论：

1. 方法与段落在本题集上完全等价（覆盖率逐题相同），因为这份代码每个方法之间都有空行，段落边界就是方法边界。换一份没有空行的代码，两者会分开。
2. 定长一套不能用来回答"某个方法怎么走的"：400 字符窗口平均只盖住期望方法的 12%–34%，8 题只有 1 题过半。做定长切片适合"找某段代码里出现过什么字眼"，不适合流程类问题。
3. 第 1、2 题首位偏了，但不是答错。`borrowBook` 分别排在 Top-4 与 Top-2，端到端答案引的是 `223-248` 与 `247-250`，内容正确。这两题的问题在于 `showBook` 打印了"状态""借出日期"这些字眼，字面更像问题。要修得从粒度或重排入手，不是改 prompt 能解决的。

端到端问答实测两条：

- C 模式「归还图书的流程是什么？」→ 5 条证据（0.7019 / 0.6065 / 0.6024 / 0.5983 / 0.5937），答案引 `(bookBorrowSystem.java 257-303)`，附图关系 12 条（DECLARES / CALLS / REFERENCES），1780ms。
- B 模式「借书前需要检查哪些条件？」→ 首位是 `showBook`，但答案正确引到 `223-228`、`229-232`、`233-244`、`245-248` 四段判断，说明 Top-5 里 `borrowBook` 起了作用。
