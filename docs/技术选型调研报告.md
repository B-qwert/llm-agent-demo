# 基于代码知识图谱与大模型的业务逻辑智能问询系统

**技术选型调研报告**

调研范围：图数据库、向量数据库与大模型 API

报告日期：2026 年 9 月 16 日

## 1 调研结论

本项目采用“代码解析与知识图谱构建 - 图检索和向量检索 - 大模型生成与引用返回”的技术路线。综合业务逻辑关系表达、语义检索能力、Windows 本地部署便利性、Python 生态、社区成熟度和项目周期等因素，确定 Neo4j 作为图数据库、Milvus 作为向量数据库、DeepSeek API 作为大模型服务，并采用 Docker Desktop、WSL 2 和 Docker Compose 完成本地开发环境部署。

该组合将确定性的代码结构关系与非结构化的自然语言语义检索分开存储和查询：Neo4j 保存模块、类、函数、接口、调用、依赖等可追溯关系；Milvus 保存代码片段、注释和业务语义卡片的向量；LLM 负责理解用户问题、组织检索和基于证据生成回答。该架构适合回答“某项业务规则在哪里实现”“接口调用链经过哪些模块”“修改某函数会影响哪些业务流程”等问题。

## 2 项目需求与评价方法

课题的核心需求是对多文件代码库建立可查询、可更新、可解释的业务逻辑索引，并支持自然语言问询。技术选型不以单项性能指标为唯一依据，而以三人小组可在既定周期内复现、维护和验收为目标。

| 评价维度 | 具体要求 | 权重 |
| --- | --- | --- |
| 功能匹配 | 支持代码关系表达、语义检索或自然语言生成，并能服务于业务逻辑问询。 | 30% |
| 工程可用性 | 支持 Docker 部署、Python 调用、本地开发和故障排查。 | 25% |
| 可解释与可追溯 | 能够返回图路径、源码定位、向量来源或引用证据。 | 20% |
| 生态与文档 | 社区活跃、文档完善、示例充分，便于三人协作维护。 | 15% |
| 成本与扩展 | 具有开源或低成本起步方案，后续可按数据规模扩展。 | 10% |

## 3 图数据库选型

图数据库用于保存静态解析得到的代码实体和关系。初期 Schema 以 Repository、Directory、File、Class、Function、Method、API、BusinessRule 等节点，以及 CONTAINS、DECLARES、CALLS、IMPORTS、IMPLEMENTS、DEPENDS_ON、BELONGS_TO 等关系为主。代码属性图研究表明，将语法、控制流和依赖关系组织为统一图结构，能够支持复杂路径查询和程序理解。

| 候选方案 | 优势 | 局限 | 结论 |
| --- | --- | --- | --- |
| Neo4j | 属性图模型直观；Cypher 易学；Browser 可视化完善；Python 驱动和 Docker 支持成熟。 | 社区版面向单机开发；大规模集群需另行规划。 | 选择 |
| NebulaGraph | 分布式图存储能力较强；适合超大规模图数据。 | 运维和学习成本相对更高；本课题初期规模不需要分布式能力。 | 备选 |
| JanusGraph | 可结合多种底层存储；适合复杂分布式场景。 | 组件较多，部署、调优和维护成本较高。 | 不选 |

最终选择 Neo4j。原因是代码调用链、依赖链和影响范围分析天然适合属性图的节点 - 关系 - 属性模型；Cypher 可以直接表达多跳路径查询；Neo4j Browser 有利于调试和展示图谱。当前开发环境使用 neo4j:5.26.12，Bolt 端口为 7687，Browser 端口为 7474，均仅绑定本机回环地址。

## 4 向量数据库选型

向量数据库用于补充图谱的结构检索能力。代码中的注释、函数语义、业务术语和自然语言问题存在表达差异，向量检索可以从问题中召回相关代码片段，再由图查询扩展调用链和上下游关系。

| 候选方案 | 优势 | 局限 | 结论 |
| --- | --- | --- | --- |
| Milvus | 独立向量数据库；支持 collection、标量过滤、近似最近邻搜索和后续扩展；Python SDK 成熟。 | Standalone 部署依赖 etcd 与 MinIO，组件数量多于嵌入式方案。 | 选择 |
| FAISS | 检索库轻量，适合算法验证和本地实验。 | 不是完整数据库；持久化、元数据过滤和多用户服务需自行实现。 | 备选 |
| Chroma | 原型搭建快，Python 使用简单。 | 大规模索引、运维和复杂检索能力不作为本项目的优先优势。 | 备选 |
| pgvector | 可与 PostgreSQL 业务数据共存，SQL 生态成熟。 | 本项目已采用图数据库处理结构关系，另引入关系数据库会增加数据同步边界。 | 不选 |

最终选择 Milvus。它能够保存向量、主键和源码定位等字段，并支持相似度搜索与标量过滤，适合实现“语义召回 + symbol_id 精确定位 + Neo4j 图扩展”的混合检索。当前开发环境使用 milvusdb/milvus:v2.6.21 和 pymilvus==2.6.6，服务端口为 19530，健康检查端口为 9091。

## 5 大模型 API 选型

LLM 服务负责问题意图理解、检索路由、证据整理和自然语言回答。为降低工程耦合，系统采用 OpenAI 兼容的 Chat Completions 接口封装，大模型名称、基础地址、超时和生成参数均通过本机 .env 配置，而非写入源代码。

| 候选方案 | 优势 | 局限 | 结论 |
| --- | --- | --- | --- |
| DeepSeek API | 提供 OpenAI 兼容接口；中文代码问答场景适配方便；可直接接入现有 Python 客户端。 | 调用依赖网络和账户额度；模型版本与价格需持续关注。 | 选择 |
| Qwen API | 中文能力和工具生态较完善；存在多种模型规格。 | 需要重新完成接口、成本和模型效果的对比验证。 | 备选 |
| OpenAI API | 工具调用与生态成熟，文档完整。 | 成本、网络可达性和数据合规要求需按具体使用场景评估。 | 备选 |

最终选择 DeepSeek API。当前配置基础地址为 https://api.deepseek.com，模型名为 deepseek-v4-flash，连通性测试采用禁用思考模式和较小输出 Token 预算，以降低测试成本。DeepSeek 官方当前说明旧模型名 deepseek-v4-flash 仍可调用，但会被路由至 DeepSeek-V4.1-Flash；后续正式联调时应评估改用官方当前推荐的 deepseek-flash 名称，并在报告中记录实际模型版本。

## 6 总体架构与部署方案

系统采用双索引架构。代码解析模块输出结构化实体和关系到 Neo4j，同时将函数、类、文件和语义卡片转换为向量写入 Milvus。用户提问后，问答编排模块首先识别问题类型：关系型问题优先查询 Neo4j；语义型问题优先检索 Milvus；涉及业务流程或影响范围的问题采用两者融合。LLM 基于检索结果生成答案，并返回节点、关系路径、symbol_id 或源码位置作为引用。

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 数据抽取层 | 代码解析器、文档抽取器 | 提取文件、类、函数、调用关系、业务语义与源码位置。 |
| 结构索引层 | Neo4j | 保存代码实体、调用链、依赖链和业务关系，支持 Cypher 路径查询。 |
| 语义索引层 | Milvus | 保存代码片段和语义卡片向量，执行相似度召回和标量过滤。 |
| 问答编排层 | Python 客户端、DeepSeek API | 执行问题分类、检索组合、提示词组织和带引用回答。 |
| 运维验证层 | Docker Compose、GitHub Actions、检查脚本 | 实现可复现部署、连通性测试和持续集成。 |

## 8 风险与后续工作

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 代码解析不完整 | 调用关系或业务链路遗漏，影响回答可信度。 | 保留源码定位；为解析器建立回归样例；区分确定事实和模型推断。 |
| 向量召回偏差 | 相关代码未进入 LLM 上下文。 | 结合关键词、元数据过滤、图扩展和人工标注问题集评测。 |
| LLM 幻觉或版本变化 | 回答可能缺少证据，模型行为可能发生变化。 | 强制返回引用；记录模型名和参数；定期复测并控制 Token 预算。 |
| 数据同步滞后 | 代码更新后图谱和向量索引过期。 | 设计增量更新机制，覆盖新增、修改、删除和重命名。 |
| 本地环境差异 | 成员难以复现部署或测试。 | 固定镜像和 Python 依赖版本；统一使用 Docker Compose 与 dev.ps1 脚本。 |

下一阶段将完成代码知识图谱 Schema、解析样例和增量更新方案；随后实现混合检索、证据引用和问答界面；最终建立覆盖检索正确性、回答正确性、引用完整性、响应时间和人工满意度的评测集与评估报告。
