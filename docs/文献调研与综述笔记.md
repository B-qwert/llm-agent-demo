# 文献调研与综述笔记


## 一、研究问题与总体认识

本课题希望回答“某个业务动作从入口到结果经过哪些代码路径、为何如此处理、证据在哪里”等问题。软件项目知识散落在源代码、配置、接口文档和说明材料中；单独阅读一个函数，往往无法还原跨文件调用和业务状态变化。三份笔记共同指出：**代码结构关系、自然语言语义匹配和带证据的答案生成必须结合**。[2–4][8][10–14]

现有方法各有适用范围。代码知识图谱能明确表示调用、继承、依赖等关系，适合回答确定的结构问题；向量检索适合从自然语言描述出发发现候选代码，但相似片段不一定处于真实调用链中；RAG 可让大模型依据检索结果回答，却仍需要核对引用与事实。仓库级任务还要求跨文件组织上下文，代码变更则要求索引保持更新。[2–4][8][10–14][16]

因此，本课题的研究重点可表述为：**如何构建可溯源的代码知识图谱与代码向量索引，依据问题类型进行图、向量和源码的联合检索，再生成能够逐项核对证据的业务逻辑回答。**这是一条由现有研究支持的拟议路线，尚需通过项目实验验证效果。

## 二、相关研究的综合归纳

| 方向 | 代表文献 | 主要启发 | 对本课题的限制或待验证点 |
| --- | --- | --- | --- |
| 知识图谱与代码结构 | 知识图谱综述、代码属性图、GraphGen4Code、CAJP [1–4] | 将文件、类、方法、接口及其关系组织成可查询的图；代码与文档可关联 | 图谱的关系定义、跨语言解析、业务概念对齐和增量更新需在项目内验证 |
| 代码语义与仓库级检索 | CodeSearchNet、CodeBERT、GraphCodeBERT、RepoCoder、代码大模型综述 [5–9] | 以自然语言发现候选代码，利用数据流和跨文件上下文补足纯文本表示 | 检索粒度、候选覆盖率与跨文件路径还原需要实测 |
| RAG、GraphRAG 与工具调用 | RAG、RAG 综述、Milvus、GraphRAG、GraphRAG 综述、ReAct [10–15] | 图查询、向量检索、模块摘要和源码读取可以作为不同证据获取路径 | 文档社区摘要的结果不能直接等同于代码调用关系；路由和融合策略需要消融对比 |
| 可信评测 | KGQA Leaderboard、Ragas、ARES、SWE-bench [16–19] | 分开检查检索、图路径、回答忠实性与任务完成情况，并固定评测版本 | 自动评分不能代替人工核对；SWE-bench 的代码修复任务与本课题问答任务不同 |

### 2.1 图谱：表示结构，但业务语义仍需对齐

知识图谱提供实体、关系与属性的表示框架[1]。代码属性图将语法、控制流和程序依赖放入统一结构[2]；GraphGen4Code 与 CAJP 分别展示大规模代码图谱构建、多源项目资料与图查询问答的可能性[3–4]。这些工作支持以“文件—类—方法—调用关系”为骨架建图，再挂接接口文档、配置和业务说明。夏高婷笔记强调，支付、订单等业务问题还涉及状态流转、权限和事务等语义；这些内容不能仅凭方法名推断，应给出源码或文档证据，区分静态解析事实与模型归纳。

### 2.2 向量检索：定位候选代码，但要验证关系

CodeSearchNet 提供自然语言到代码检索的基准思路[5]；CodeBERT 将自然语言和程序语言映射到可比较的表示[6]；GraphCodeBERT 说明数据流信息有助于代码语义建模[7]。RepoCoder 把检索范围扩大到仓库级上下文[8]。据此，本课题宜以方法或函数为主要索引单元，保留所属文件、类、模块和提交版本，并对入口函数、被调用函数及邻近说明建立关联。切片大小与 Embedding 模型应根据本项目问题集比较，不预设某个模型最佳。

### 2.3 混合检索与回答：按问题取得不同证据

RAG 的基础是先获取外部知识，再据此生成回答[10–11]。GraphRAG 则提供图索引、图引导检索与全局概括的研究思路[13–14]。对于“谁调用了某方法”，优先用图查询或可验证的源码分析；对于“哪里实现了订单超时处理”，先用语义检索找候选，再在图中扩展调用关系；对于“某模块整体做什么”，可以结合模块文档与摘要。ReAct 为模型调用图查询、向量检索和源码读取工具提供了参考[15]。**上述路由是本课题的设计假设，不是这些论文已经在本项目上验证的性能结论。**

检索结果应统一携带项目版本、文件路径、符号名、代码行范围和证据类型。答案中的调用关系必须能回查到图边或源码；业务解释若只是模型推断，应标注不确定性。Milvus 可承载向量索引[12]，项目当前开发基线也已选用 Milvus；是否另做轻量索引对比，可在实验设计时决定。

### 2.4 评测：把“找到”“说对”“可核对”分开

三份笔记一致认为，单看回答是否通顺不足以说明系统有效。[16–19] 本课题可按以下层次建立评测：

1. **图谱层**：抽样核对实体、调用边和源码位置；记录解析失败、动态调用及跨语言关系的覆盖情况。
2. **检索层**：对标准证据集合测量 Recall@K、MRR 或排序质量，并比较纯向量、纯图和混合方案。[5]
3. **回答层**：由人工核对事实正确性、证据覆盖、引用准确率和无证据断言；Ragas、ARES 的相关性与忠实性指标可辅助分析。[18–19]
4. **任务层**：以真实仓库中的单跳、跨文件多跳、业务流程、异常分支等问题检查完成率；借鉴 SWE-bench 的真实任务与可复现环境思想，但不把“修复代码通过测试”直接当作问答正确率。[16]

分工表计划在后续阶段构建 **50 个业务问题**；当前文献汇总先提出题型和评价方法，标准答案、证据路径与评分规则仍需单独制定。评测报告应记录仓库提交、图谱/索引版本、模型和提示词版本，以便复现。

## 三、拟议技术路线与研究难点

1. **数据准备**：解析源代码并抽取文件、类、方法、字段及调用、继承、导入等关系；把文档与配置中的相关说明连接到代码符号。[2–4]
2. **双索引构建**：在 Neo4j 中存放结构关系，在 Milvus 中存放带源码定位信息的代码与文档向量；两者使用稳定的符号标识关联。[3–4][12]
3. **查询与证据融合**：识别问题所需的实体与任务类型，组合语义召回、图谱子图扩展和源码读取，再对候选证据排序。[8][11][13–15]
4. **受证据约束的生成**：输出业务流程、调用路径与逐项引用；证据不足时明确指出缺口，避免补造不存在的函数或关系。[10–11][18–19]
5. **更新与评估**：代码变更后同步图谱、向量和定位信息；按上述四层指标比较方案，并分析错误来源。[16–19]

需要重点研究的难点是：代码切片在检索精度与上下文完整性之间如何取舍；自然语言业务概念怎样映射到代码实体；动态调用和长调用链怎样表示与裁剪；图谱、向量和文档版本怎样保持一致。这些均来自三份笔记的综合判断，尚非已完成的实验结论。
