# 业务逻辑智能问询系统深化设计文档

## 1. 总体设计

浏览器提供问询工作台和历史记录页，Python HTTP 后端处理索引准备、问答和记录读写。Ollama 生成代码和问题的向量，Milvus 检索相近片段，Neo4j 提供代码关系，DeepSeek 根据问题和本次提供的证据生成回答。

| 模块 | 实现位置 | 职责 |
| --- | --- | --- |
| 页面 | `web/` | 选择模式及切分方式、发起问答、展开证据、导出记录 |
| HTTP 服务 | [server.py](../bizcodeqa/platform/server.py) | 接收 JSON，返回状态、历史及结果，控制任务互斥 |
| 样例与切分 | [sample.py](../bizcodeqa/platform/sample.py)、[chunking.py](../bizcodeqa/platform/chunking.py) | 核对源码摘要，生成样例图数据和代码片段 |
| 索引准备 | [prepare.py](../bizcodeqa/platform/prepare.py) | 生成向量、写入两类数据库、登记可用索引 |
| 检索与问答 | [stores.py](../bizcodeqa/platform/stores.py)、[qa.py](../bizcodeqa/platform/qa.py) | 向量召回、图扩展、证据组装、编号检查 |
| 模型调用 | [llm.py](../bizcodeqa/llm.py) | 请求 Chat Completions 接口，检查响应并返回模型信息 |

## 2. 索引与问答流程

### 2.1 准备索引

读取图书借阅样例和快照清单，将源码换行统一为 LF 后核对 SHA256 和行数。方法、字段及调用关系来自人工核对的样例数据。Tree-sitter 用于 AST 语句切分。

| 切分方式 | 片段规则 | 本样例片段数 |
| --- | --- | ---: |
| 方法/字段 | 完整方法、单个字段 | 20 |
| 固定字符 | 按 Unicode 字符窗口，默认 800 字符、重叠 100 字符 | 19 |
| AST 语句 | 方法体直接子语句、字段声明，复合语句整体保留 | 135 |
| Token | 固定 Qwen 分词器，默认 800 Token、重叠 100 Token | 5 |
| 空行段落 | 空行分隔，段落整体保留 | 15 |

后端将符号规范名和代码交给 Ollama，校验向量数量和维度后写入新建的 Milvus 集合。图谱按实体键、关系键写入 Neo4j。核对向量条数和图实体数后，用临时文件替换对应的本地索引登记。激活前失败时，原登记仍可读取，后端会尝试清理此次新建的向量集合。

### 2.2 处理问题

1. **A 直接问答。** 只将当前问题交给 DeepSeek。
2. **B 向量检索问答。** 读取所选策略的索引，校验源码快照及 Embedding 模型摘要和维度。将问题向量用于 Milvus 的 Top-K 查询，按仓库和快照筛选。方法/字段模式的向量查询限定为 Method。
3. **C 图谱扩展问答。** 以 B 的命中片段作为种子，在同一快照内查询调用关系、字段引用和共用字段的方法。片段去重后最多追加 3 块，再组装回答所需证据。

入模时先放向量块，再放图扩展块，源码字符预算为 18000。放不下的整块跳过，剩余证据依次编号为 `[E1]`、`[E2]` 等。模型返回后，后端检查编号是否存在，并提示缺失引用。成功问答追加保存，随后由页面显示回答、证据和耗时。

## 3. HTTP 接口设计

平台默认在本机 8765 端口运行。POST 使用 UTF-8 JSON，题目最多 2000 个字符，`top_k` 为 1 至 5 的整数，默认 5。索引准备和问答共用一把任务锁。

| 方法与路径 | 请求 | 成功结果 |
| --- | --- | --- |
| GET `/api/status` | 无 | 模型配置状态、各切分索引登记、准备进度、历史条数 |
| GET `/api/history` | 无 | `{"records": [...]}`，返回全部已保存的问答 |
| POST `/api/prepare` | 切分方式及参数 | HTTP 202，返回 `preparation`。页面通过状态接口查看任务结果。 |
| POST `/api/chat` | 模式、问题、Top-K 和切分配置 | HTTP 200，返回答案、证据及本次执行信息 |

准备字符索引的请求：

```json
{
  "chunking_strategy": "character",
  "chunk_size": 800,
  "chunk_overlap": 100
}
```

使用方法/字段索引提问的请求：

```json
{
  "mode": "C",
  "question": "借书前检查哪些条件？",
  "top_k": 5,
  "chunking_strategy": "method"
}
```

切分值为 `method`、`character`、`ast`、`token`、`paragraph`。问答响应的 `answer` 是模型回答，`evidence` 保存源码片段、证据编号及来源，`graph_paths` 保存关系路径。`timings`、`collection`、`snapshot_id` 和模型字段用于查回本次执行。

| 错误码 | 触发情况 |
| --- | --- |
| 400 | JSON、字段或取值无效 |
| 403 | 本机地址或请求来源校验失败 |
| 404 | 页面资源或接口不存在 |
| 409 | 已有问答或索引准备任务 |
| 413 / 415 | 请求体长度超限或内容类型错误 |
| 502 / 503 | 模型调用失败 / 索引或检索依赖不可用 |
| 500 | 后台任务启动失败或其他平台请求错误 |

## 4. 数据库设计

### 4.1 Neo4j

样例图包含 23 个节点和 80 条关系。节点使用 `CodeEntity` 公共标签和具体类型标签，保存仓库、快照、提交、规范名和适用的源码位置。

| 实体或关系 | 存储内容 |
| --- | --- |
| Repository → File | `CONTAINS`，记录仓库与文件的归属 |
| File → Class、Class → Method/Field | `DECLARES`，记录声明位置和归属 |
| Method → Method | `CALLS`，记录样例中核对过的调用及发生位置 |
| Method → Field | `REFERENCES`，记录每个方法对该字段的首个核对位置及访问类型 |

`snapshot_id` 由仓库标识和完整提交号组成，`symbol_id` 标识源码符号，`entity_key` 将符号限定到具体快照。数据库对 `entity_key` 建立唯一约束，对 `snapshot_id` 和 `symbol_id` 建立查询索引。关系使用 `relationship_key` 合并写入。字段和方向遵循 [Schema 设计规范](Schema设计规范.md)，实际建库语句见 [Neo4j 脚本](../bizcodeqa/platform/neo4j_schema.cypher)。

### 4.2 Milvus

每次准备索引时新建一个集合，集合名称包含切分配置、提交摘要、模型摘要和随机后缀。检索使用本地登记指向的集合。

| 字段或配置 | 定义 |
| --- | --- |
| `chunk_id` | VARCHAR(256) 主键，应用生成 |
| `vector` | FLOAT_VECTOR，维度由 Embedding 输出确定，现有样例登记为 1024 |
| 动态字段 | 快照、符号、路径、行号、摘要、模型及切分信息 |
| 检索索引 | FLAT，COSINE，相似度查询使用 Strong 一致性 |

Milvus 返回片段主键，后端用该主键从本地索引登记取出代码。片段关联的 `symbol_id` 或 `symbol_ids` 再用于定位 Neo4j 节点。

### 4.3 本地文件与部署

| 位置 | 内容 |
| --- | --- |
| `samples/book_borrow/snapshot.json` | 样例源码版本、路径、行数及摘要 |
| `reports/platform/index.json` | 方法/字段索引登记及代码片段 |
| `reports/platform/index_<profile_id>.json` | 其他切分配置的集合、片段及模型登记 |
| `reports/platform/graph_fixture.json` | 样例图数据与未解析引用 |
| `reports/platform/history.jsonl` | 追加保存成功问答、证据、模型配置和耗时 |

Neo4j 和 Milvus 通过 Docker Compose 启动，数据写入命名卷。问询平台可以在宿主机或容器运行，网页端口绑定本机。服务地址和密钥由 `.env` 配置。部署和启动命令见 [问询平台使用说明](问询平台使用说明.md)。
