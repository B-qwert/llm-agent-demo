### 2.3 代码召回率：统一按必要证据单元统计

每题的 `G1、G2…` 是必要证据单元，仅在题内编号。五种切分共用同一组证据单元，各单元等权。命中以覆盖支持结论的实际代码为准。

判定规则：

1. 仓库、提交和文件必须一致。
2. 对照单元指定行范围及关键代码检查。多个片段的并集完整覆盖该单元所需代码，计 1；仅含名称或一部分关键条件，计 0，并备注部分覆盖。
3. 以实际片段原文／字节区间为准。字符或 Token 片段的起止行可能只覆盖某行的一部分，不能看到行号相交就判命中。
4. 对同一单元，重叠片段或多次召回只计 1；不同单元即使部分源码重叠，也各按已冻结的定义判断。
5. 判断“没有某个检查”时，须另行人工核查完整方法；只召回输入语句不能证明不存在检查。召回率仍按下表正向支撑单元统计，否定结论的完整性单独记录，避免把全文审计要求混入片段召回分母。
6. Q11 的全文件“没有持久化实现”是另行人工审计结论，不把全文缺失证明混入普通 Top-K 召回分母；其 G1—G3 仅衡量正向支撑代码是否召回。

```text
某题证据召回率 = 命中的必要证据单元数 / 该题必要证据单元总数
宏平均召回率 = 14 道题各自召回率之和 / 14
微平均召回率 = 14 道题命中单元数之和 / 14 道题单元总数之和
```

召回率按以下阶段统计。

| 指标 | 统计候选集合 |
| --- | --- |
| 向量 Recall@K | 未经上下文裁剪的最初 K 个向量返回片段 |
| 图扩展后召回率 | 向量片段＋图补充片段，尚未经过上下文预算裁剪 |
| 最终证据召回率 | 实际送给模型的 evidence 片段 |

JSON 的 `evidence` 保存预算筛选后进入模型的片段，`origin` 标记向量或图谱来源。预算筛选前的完整候选未单独保存。

返回的向量片段数等于 K 且无额外过滤时，可据此计算向量 Recall@K。片段数少于 K 时，导出记录无法区分召回不足和预算剔除。缺少原始候选的阶段标为「原始阶段数据不足」。

A 不进行检索，召回率记 **N/A**，不记为 0，也不加入 B/C 召回率汇总。五种切分的相同 K 代表不同代码量，还需记录最终代码字符数及上下文长度，解释比较限制。

### 本轮验证结论

1. A 模式的 70 条回答均未得满分。加入源码检索后，方法/字段切分的 B 和 C 均答对 13/14 题（92.86%），最终证据微平均召回率均为 88.89%（32/36）。两组都漏召回了 Q13 的初始化代码。
2. Token 切分的 B 答对 14/14 题，C 答对 13/14 题。该索引一共 5 块，Top-5 取回了全文，B 和 C 的证据召回率均为 100%。这一结果适用于本批样例和检索配置。
3. 加入图谱后，字符切分的最终证据微平均召回率从 80.56% 升至 86.11%，段落切分从 80.56% 升至 83.33%。新增证据均来自 Q11。字符切分的正确率持平，段落切分从 12 道满分题降到 11 道。
4. AST 语句切分的 B 和 C 最终证据微平均召回率均为 33.33%，完全正确率分别为 35.71% 和 28.57%。这批结果中，有些片段只取回了字段或输出语句，缺少关键业务分支。
