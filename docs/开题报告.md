# 基于代码知识图谱与大模型的业务逻辑智能问询系统关键技术研究与实现开题报告

撰写人：白乐刚；项目团队：白乐刚、夏高婷、周笑彤。撰写日期：2026 年 9 月 28 日。研究方案与指标需在后续实验中验证。

## 一、选题背景与研究意义

企业级软件的业务规则分散在源代码、配置、接口与数据库映射中。一项“订单取消”或“支付成功后处理”的行为可能跨越控制器、服务、数据访问层及外部接口。关键词搜索能定位名称相近的文件，却不一定还原真实调用链；只读取单个函数也难以解释状态变化、异常分支和事务边界。大模型可以概括代码，但在缺少完整仓库证据时，可能把语义上相似的片段误当作实际调用关系。代码属性图研究表明，程序语法、控制流等结构信息可以组织为可查询的图[1]；代码知识图谱和代码图数据库研究进一步展示了仓库级结构索引的可行性[2–3]。

本课题面向开发者、新成员和架构分析人员，研究如何从源码建立可溯源的结构关系，结合自然语言语义检索寻找相关代码，再让大模型依据图路径与源码位置回答业务问题。预期价值有两方面：在研究上，探索程序结构、业务语义和生成式问答之间的证据融合机制；在工程上，为业务流程理解、需求变更影响分析和故障排查提供可复核的辅助工具。系统结论只应说明源码证据支持的范围；不能从静态调用图直接推断运行时必然执行的路径。

## 二、国内外研究现状与问题分析

**代码结构与图谱。**代码属性图将多类程序分析信息合并查询，适合表示确定性的代码关系[1]。GraphGen4Code 将类、函数、调用使用关系及文档连接为代码知识图谱[2]；CodexGraph 使大模型通过代码图数据库获得仓库级上下文[3]。这些工作提供了结构化索引和工具接口的基础，但本课题仍需处理业务概念与代码符号的对齐，以及静态解析无法确认动态分派、反射等关系的边界。

**语义检索与仓库级上下文。**CodeSearchNet 为自然语言代码检索提供了基准任务[4]；CodeBERT 研究自然语言与程序语言的联合表示[5]。RepoCoder 利用仓库内跨文件上下文改进代码补全[6]，说明仅依赖当前文件不足以覆盖仓库级信息。不过，语义相近并不等于存在调用或依赖关系，向量召回的候选仍需由图谱和源码核实。

**生成式问答与评测。**RAG 将外部检索结果引入生成过程[7]；GraphRAG 针对文档集合的全局问题提出图组织与摘要方法[8]，其文档图不能直接等同于由程序分析得到的代码调用图。ReAct 为模型交替推理与调用外部工具提供方法参考[9]。RAGAs 和 ARES 将检索相关性、答案忠实性等维度拆开评估[10–11]。本课题应在自动评测之外保留人工源码核对，避免把流畅回答误判为正确业务逻辑。

国内研究已从代码知识图谱的建模与表示、构建与精化、存储与演化、查询理解及智能应用等方面梳理关键问题[12]。结合现有课题资料和上述研究，本课题的具体缺口是：多文件业务问题需要跨符号关系的完整证据；业务术语与代码命名不总一致；图谱、向量索引和源码版本可能不同步；生成答案需要逐项核验引用。上述判断是开题阶段的问题分析，不预设本系统的性能优于已有方法。

## 三、研究目标、范围与关键问题

总体目标是实现一个面向代码仓库的业务逻辑问询原型：用户提出自然语言问题后，系统返回业务解释、相关调用或依赖路径，以及可点击或可定位的文件与行号证据。研究对象优先选择可公开使用、具有典型业务流程的 Java 样例项目；先完成单语言可复现实验，再评估扩展至其他语言的成本。仓库中现有的 Neo4j、Milvus 和 DeepSeek 接入属于开发底座，尚不等于问询系统已实现。

需回答的关键问题如下：

1. **结构事实抽取：**如何从 AST/Tree-sitter 解析结果中稳定识别文件、类、方法和调用等实体关系，并记录解析方式与不确定性？
2. **业务语义关联：**如何把“订单”“取消”“补偿”等业务词与代码实体、状态变化及配置关联，避免仅凭命名生成无证据解释？
3. **混合检索：**面对精确符号查询、模糊业务查询与跨模块影响分析，如何组合符号检索、向量召回和限定范围的图遍历？
4. **可信回答：**如何让每条关键结论都指向同一代码版本的源码行或图关系，并在证据不足时明确拒答或标注不确定性？
5. **持续更新：**代码提交后如何识别受影响的符号，协调更新图谱、向量索引及其版本标记，并检测过期引用？

课题原始方案提出较高的规模与准确性目标。开题阶段将其作为努力方向，不把百万行规模、准确率或增量延迟写成已验证能力。正式验收以可复现实验和明确的样本范围为准。

## 四、研究内容与拟采用的方法

### 4.1 代码结构抽取与图谱建模

设计统一的实体与关系 Schema。基础实体包括 `Repository`、`File`、`Class`、`Method`、`Function`、`API` 和 `BusinessConcept`；基础关系包括 `CONTAINS`、`DECLARES`、`CALLS`、`IMPORTS`、`IMPLEMENTS` 与 `MENTIONS`。每个符号记录仓库提交号、文件路径、起止行、语言和稳定标识；每条关系记录抽取来源、调用位置及可信级别。先用静态解析建立可确认关系，再在有必要时使用语言服务或人工核对补充跨文件引用。动态调用、反射和框架注入产生的关系应单独标注为“未确定”或“推断”，不得混入确定性事实。

### 4.2 业务概念与向量索引

以方法或函数为主要切片单位，保留所属类、模块、代码位置和必要的邻近上下文。为代码、注释和经核对的业务说明生成向量，写入 Milvus；向量记录与 Neo4j 节点共用稳定的符号标识及提交号。候选 Embedding 模型、切片长度和 Top-K 参数通过小规模样本比较确定，不在开题阶段预设最佳配置。模型生成的业务摘要只是候选解释，只有能回查到源码或文档依据时才进入可引用证据集。

### 4.3 图与向量的混合检索

对问题进行轻量分类：精确符号类优先符号搜索与图查询；模糊业务类先进行语义召回，再沿相关调用、实现或依赖边扩展；影响分析类从目标节点做有界反向遍历。检索结果统一转换为证据对象，包含 `commit`、`path`、`line_start`、`line_end`、`symbol_id`、证据类型及路径来源。融合排序综合语义相关性、图路径长度、实体匹配和证据完整性；图扩展设置跳数、节点数与关系类型限制，避免无界遍历。

### 4.4 受证据约束的问答原型

构建查询、检索、源码读取、生成和引用校验五个环节。大模型通过受控工具获取候选证据，以“结论—依据—源码位置—限制”组织答案。引用校验器核查文件、行号和提交版本是否存在，关键调用结论是否对应图边或源码；无证据的推断与已确认事实分开呈现。原型先实现必要的问答界面与图谱展示，Agent 多轮工具调用作为可控扩展，不以自动修改代码为研究目标。

### 4.5 增量更新与评测

根据 Git 提交差异定位变更文件及符号，重新解析受影响范围，并同步更新 Neo4j 与 Milvus。采用提交号作为版本边界，在图与向量尚未同步完成时不向用户呈现跨版本混合证据。评测除结果质量外，还记录全量构建时间、单次变更更新时间、失败恢复和陈旧引用比例。

技术链路可概括为：

```text
目标代码仓库与提交号
  → 静态解析与符号定位
  → Neo4j 结构图谱 ─────────────┐
  → 代码切片与向量化 → Milvus ──┼→ 问题路由与证据融合
  → 源码/文档原文读取 ──────────┘              ↓
                                     DeepSeek 生成与引用校验
                                               ↓
                                     可追溯回答或证据不足说明
```

## 五、技术选型与前期工作基础

项目现有仓库已配置 Python 3.12 验收容器、Docker Compose、Neo4j 5.26.12、Milvus 2.6.21、etcd、MinIO 和 DeepSeek 兼容 API 客户端。Neo4j 负责结构实体与关系，Milvus 负责语义向量召回，DeepSeek 负责问题理解和基于证据的回答组织。`bizcodeqa/check.py` 已有数据库读写检索及 API 连通性检查；这些检查验证基础服务可用，不验证业务问答质量。技术选择的比较依据见[技术选型调研报告](技术选型调研报告.md)，环境验收记录见[开发环境成果与验收报告](开发环境成果与验收报告.md)。

已完成的研究准备包括[文献调研与综述笔记](文献调研与综述笔记.md)、全周期[团队协作规范](团队协作规范.md)及仓库 CI。尚待实现的是解析引擎、项目图谱、代码向量索引、混合检索、问答界面和评测集。研究阶段仅处理授权或开源代码；送往外部 LLM API 的源码范围需要最小化，并避免上传密钥、个人信息和未获授权的业务数据。

## 六、实验设计与评价指标

按进度计划在评估阶段建立 **50 个业务问题**，覆盖符号定位、调用链、跨模块流程、异常分支、状态变化及影响范围。每题人工标注问题类型、可接受答案要点、必要证据的文件与行号、仓库提交号；对无法由静态代码确定的问题标注“不足以判断”。标注者复核分歧并留存判定依据，避免用模型生成答案直接充当真值。

设置三组主要对照：纯文本/向量检索加生成、只用图或符号关系检索加生成、拟议的图向量混合检索加生成。三组使用同一仓库版本、问题集和模型设置；另做去除问题路由、图扩展、引用校验的消融实验。对于无证据问题，单独测量拒答或不确定性表达是否恰当。

| 评价层次 | 指标与计算口径 | 验证方式 |
| --- | --- | --- |
| 解析与图谱 | 实体/关系抽样准确率、可确认调用边召回率 | 人工对照源码及解析记录；单列动态调用未确定项 |
| 检索 | Recall@K、MRR、必要证据 Top-3 命中率 | 与每题人工标注的证据集合比较 |
| 回答 | 要点正确率、引用有效率、无证据断言比例 | 双人核查答案、行号及对应源码；分歧复议 |
| 更新与性能 | 索引构建时间、增量更新 p95、陈旧引用比例、问答延迟 p95 | 固定机器配置和仓库提交，重复运行并报告分布 |

原课题提出 Top-3 准确率不低于 85%、答案可追溯率 100%、结构性幻觉率低于 5% 等目标。本报告将“Top-3”具体化为**必要证据在前三个候选中命中**，将“可追溯”定义为**每个有效回答的关键结论都有可打开的同版本源码或图关系引用**；具体阈值能否达到，以 50 题评测结果为准。若样本量不足以支持稳定统计结论，应同时报告分题型结果与典型失败案例，而不是仅给总体百分比。

## 七、预期创新点、可行性与风险控制

拟验证的创新点是：以确定性代码图谱作为结构事实层，另建有证据来源的业务概念层；根据问题类型动态组合向量召回和图遍历；将提交版本与文件行号贯穿检索、生成和校验；用增量更新保持两类索引一致。这些是研究设计与待验证假设，并非已取得的创新成果。

可行性来自已搭建的数据库和 LLM 开发底座、现有论文和工具链，以及三人进度计划中的模块分工。主要风险及处置如下：

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 动态调用、反射或框架注入使静态调用图不完整 | 影响链漏报或误报 | 明示关系来源与可信级别；必要时结合语言服务或人工核验 |
| 业务词与代码命名差异大 | 语义召回遗漏 | 结合业务词典、别名和多粒度切片；以标注问题集调整策略 |
| 图谱与向量索引版本不一致 | 引用过期、回答失真 | 统一提交号；更新过程设置一致性检查和回滚记录 |
| 外部 API 的成本、限流或敏感代码限制 | 实验难以复现或数据外泄 | 固定测试集与调用预算；最小化发送上下文；必要时评估本地模型替代 |
| 目标规模和进度过于激进 | 原型难在周期内稳定完成 | 先交付单语言端到端原型，再逐项扩展语言、规模和 Agent 能力 |
