### 2.3 代码召回率：统一按必要证据单元统计

每题下表的 `G1、G2…` 是**必要证据单元**，仅在本题内编号。五种切分使用同一组单元，不能按方法片段、AST 节点或 chunk_id 各自定义分母。每个单元等权；宽泛“相关方法名”只作定位，命中必须包含表中支持该结论的实际代码。

判定规则：

1. 仓库、提交和文件必须一致。
2. 对照单元指定行范围及关键代码检查。多个片段的并集完整覆盖该单元所需代码，计 1；仅含名称或一部分关键条件，计 0，并备注部分覆盖。
3. 以实际片段原文／字节区间为准。字符或 Token 片段的起止行可能只覆盖某行的一部分，不能看到行号相交就判命中。
4. 对同一单元，重叠片段或多次召回只计 1；不同单元即使部分源码重叠，也各按已冻结的定义判断。
5. 判断“没有某个检查”时，须另行人工核查完整方法；只召回输入语句不能证明不存在检查。召回率仍按下表正向支撑单元统计，否定结论的完整性单独记录，避免把全文审计要求混入片段召回分母。
6. Q11 的全文件“没有持久化实现”是另行人工审计结论，不把全文缺失证明混入普通 Top-K 召回分母；其 G1—G3 仅衡量正向支撑代码是否召回。

```text
某题证据召回率 = 命中的必要证据单元数 / 该题必要证据单元总数
宏平均召回率 = 14 道题各自召回率之和 / 14
微平均召回率 = 14 道题命中单元数之和 / 14 道题单元总数之和
```

同时报告阶段，不能混写：

| 指标 | 统计候选集合 |
| --- | --- |
| 向量 Recall@K | 未经上下文裁剪的最初 K 个向量返回片段 |
| 图扩展后召回率 | 向量片段＋图补充片段，尚未经过上下文预算裁剪 |
| 最终证据召回率 | 实际送给模型的 evidence 片段 |

**当前导出限制**：现有 JSON 的 `evidence` 是上下文预算筛选后的最终证据，`origin` 区分 vector／graph；没有单独保存预算筛选前的完整向量和图扩展候选。因此现阶段能够可靠人工计算的是“最终证据召回率”，以及“最终展示的向量证据召回率”。不能把预算剔除的证据当成从未检索到。

若某次返回的 vector 片段数恰好等于请求 K，且没有其他额外过滤，则可确认该次 K 个初始向量结果都保留，再据此计算向量 Recall@K；不足 K 时，仅凭导出无法区分“召回不足”与“预算剔除”，应标“原始阶段数据不足”。同理，未记录原始候选时，不虚填图扩展前后的完整指标。需要严格统计全部阶段时，后续另加日志，本次不修改平台代码。

A 不进行检索，召回率记 **N/A**，不记为 0，也不加入 B/C 召回率汇总。五种切分的相同 K 代表不同代码量，还需记录最终代码字符数及上下文长度，解释比较限制。
